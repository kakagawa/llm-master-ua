# Чому в добу агентів усі роблять CLI: Claude Code, Codex і історія командного рядка

Сьогодні про явище, що на позір видається дуже «ретро»: **AI дійшов уже до агентів — то чому найгучніші продукти, навпаки, залізли назад у чорне вікно командного рядка?**

Точніше кажучи, з CLI починав не продукт Claude як такий, а **саме Claude Code — агент для програмування, який одразу обрав CLI**. У лютому 2025 року Anthropic випустила його як research preview у терміналі; у квітні того самого року OpenAI викотила відкритий Codex CLI, а Codex Web — лише в травні.

Це не копіювання одне в одного. Обидві компанії водночас наштовхнулися на той самий інженерний факт: **чат зручний, щоб модель «говорила», а CLI — щоб агент справді «робив».**

Раніше ми розбирали цикл агента в статті [Автор Claude Code каже «пишіть не промпти, а цикли»](./claude_code_loop.md), а далі — оркестрацію й перевірку в [динамічних робочих процесах](./dynamic_workflows.md) та [Loop Engineering на практиці](./loop_engineering_guide.md). Ця стаття копає ще глибше: чому найкращим фундаментом для цих циклів виявився командний рядок, якому десятки років.

## Історія CLI: це ніколи не було просто «друкувати в чорному вікні»

Спершу розведімо три поняття: термінал — це те, що приймає ввід і показує вивід; shell — програма, що інтерпретує команди; CLI — спосіб взаємодіяти з програмою текстовими командами. Claude Code й Codex CLI сьогодні вже радше TUI — з панелями, статусами й гарячими клавішами, — але їхній справжній фундамент усе одно shell, файлова система й увесь набір інструментів командного рядка.

Найперші комп'ютери не мали навіть командного рядка. Люди пробивали програму на картках, віддавали машині на пакетну обробку й забирали результат згодом. **Живого діалогу між людиною й машиною не було.**

Потім з'явилися системи з розподілом часу й термінали, і людина нарешті могла ввести рядок команди й одразу побачити рядок результату. А в Unix shell зробив ще один ключовий крок: він став не лише входом для запуску програм, а й мовою керування, що дозволяє програми комбінувати.

`stdin`, `stdout`, `stderr`, коди виходу, перенаправлення, конвеєри — ці рішення виглядають аскетично, але саме вони зшили купу дрібних інструментів у робочі процеси. Ще у визначенні Unix Shell, яке Bourne дав 1978 року, водночас наголошено і на керуванні потоком, і на середовищі, і на перенаправленні, і на конвеєрах процесів.

Після приходу GUI командний рядок не зник. Бо GUI розв'язує **проблему пошуку для людини**: кнопки на видноті, і навіть той, хто не вміє писати команд, може натиснути. А CLI розв'язує **проблему композиції для системи**: одна команда лягає в скрипт, у CI, запускається на віддаленій машині, а її вивід можна передати наступній програмі.

У хмарну добу Git, Docker, Kubernetes, Terraform і всі хмарні платформи майже без винятку зробили CLI повноцінним громадянином. Причина проста: серверу не потрібен екран, а автоматизація не тицятиме мишкою в кнопки.

У добу агентів командний рядок зробив ще один оберт і повернувся. Але тепер головним, хто набирає команди, стає вже не людина, а модель.

![](https://file1.kamacoder.com/i/web/2026-07-16_10-48-27.jpg)

Схема показує, чому CLI не помер у добу GUI, а в добу агентів навіть вийшов на передній план. Змінилося не те, що командний рядок раптом став зручнішим, а те, що каторжна робота «перекласти людський намір у точний синтаксис» перейшла від людини до агента: саме той бар'єр, що найбільше відлякував людей від CLI, велика модель і з'їла.

## Чому агент і CLI — ідеальна пара?

Багато текстів кажуть: «CLI швидкий, легкий, гіковий». Занадто поверхово. **Агент обирає CLI не тому, що термінал крутий, а тому, що CLI від природи дає систему зворотного зв'язку, яку можна виконувати, спостерігати й комбінувати.**

Коли ви просите Claude Code полагодити баг у логіні, він не просто видає шматок коду, а може працювати далі по репозиторію: командою пошуку знайти ланцюжок викликів, прочитати файли, змінити код, прогнати юніт-тести, подивитися на помилку, перечитати diff — і так доки докази не покажуть, що задачу виконано.

Найцінніша тут не якась окрема команда, а те, що CLI стискає весь ланцюжок інструментів у єдину структуру:

- **вхід — текст або файли**: вимоги, шляхи, параметри передаються однозначно;
- **дія — команда**: можна викликати Git, компілятор, тестовий фреймворк, базу даних, хмарну платформу;
- **зворотний зв'язок — докази**: стандартний вивід, вивід помилок, код виходу, звіт тестів і diff повертаються в контекст;
- **композиція — конвеєри й скрипти**: одну вдалу взаємодію легко закріпити як відтворюваний процес;
- **межі забезпечує операційна система**: робоча тека, права на файли, мережеві політики, контейнери й пісочниці обмежують радіус ураження від дій агента.

Так утворюється повноцінний замкнений цикл.

![](https://file1.kamacoder.com/i/web/2026-07-16_10-56-58.jpg)

Схема показує, чому агентові не досить самого лише «мозку». CLI під'єднує файлову систему й готовий ланцюжок інструментів як його «руки», а stdout, stderr, коди виходу й diff стають «очима»; провалена перевірка — це вже не туманне «неправильно», а докази, які наступний раунд міркувань може спожити напряму.

І ще одна сильна річ: CLI **рекурсивний**. Агент не лише викликає CLI — він і сам може стати ланкою в CLI:

```bash
cat build-error.txt | claude -p "знайди першопричину й запропонуй виправлення"
git diff | codex exec "перевір, чи не вносить ця зміна проблем із паралельністю"
```

Інтерактивний інструмент так перетворюється на компонент скрипта, який можна пустити в CI, у заплановані задачі й у процеси без нагляду. Вебчатові це дається природно значно важче.

## То GUI програв? Ні, просто він більше для людей

Головна перевага GUI — розкласти можливості перед людиною. Макети, дашборди, складні таблиці, візуальне налагодження: усе це людині набагато зручніше побачити, ніж вичитати кількасот рядків тексту.

А от коли GUI оперує агент, він часто «вгадує пікселі»: кнопка переїхала, з'явилося ще одне вікно, сторінка довантажилася повільніше — і шлях виконання вже інший. Звісно, він може дивитися на екран і рухати мишею через Computer Use, але цей канал **має велику затримку, приховані стани, погано розпаралелюється й погано відтворюється точно**.

CLI ж дає діям імена. `git status` не поїде у правий верхній кут через зміну розміру вікна, а код виходу `1` набагато легше оцінити, ніж червоний рядок на скриншоті.

Тож справжній поділ праці — не в тому, що CLI вбиває GUI, а у двох шарах: **людина через застосунок, IDE чи веб дивиться плани, перевіряє diff і видає дозволи; агент унизу виконує й збирає докази через CLI, API та MCP.**

![](https://file1.kamacoder.com/i/web/2026-07-16_10-58-09.jpg)

Схема показує, хто кого замінює серед IDE, застосунків і CLI. Верхній інтерфейс відповідає за те, щоб пояснити складний стан людині, нижній рівень інструментів — за те, щоб віддати агентові однозначні дії; погодження й докази курсують між шарами, і ніхто не змушує людину вічно дивитися в термінал, а агента — вічно тицяти в пікселі.

## Але сьогодні багато CLI до агентів не готові

Не варто думати, ніби всі CLI надійні просто тому, що агент уміє виконувати команди. Купа старих інструментів за замовчуванням вважає оператором людину: вони питають підтвердження, малюють кольорові індикатори прогресу, підмішують помилки в stdout, а то й повертають `0` після невдачі. Людина за досвідом розбереться, а от агент у конвеєрі легко зламається.

Справді дружній до агентів CLI має щонайменше:

- підтримувати `--json` чи стабільну схему, щоб модель не вгадувала поля з барвистих логів;
- класти результат у stdout, діагностику — у stderr, а код виходу мусить чесно відображати успіх чи невдачу;
- давати `--dry-run`, diff та ідемпотентні операції, щоб агент міг спершу прорепетирувати, а після невдачі безпечно повторити;
- підтримувати неінтерактивний режим, таймаути й скасування, щоб серед ночі не зависати на «продовжити? Y/n»;
- мінімізувати права, звужуючи облікові дані за задачею, текою, командою і часом;
- лишати аудит: хто що виконав, що змінив і на якій підставі.

**Майбутня конкуренція серед CLI — це не лише зручність для людини, а й здатність бути стабільно викликаним агентом.** Структурований вивід важитиме дедалі більше, а права й пісочниці з додаткової опції перетворяться на можливість за замовчуванням.

Саме тому і Claude Code, і Codex вкладають стільки сил у модель дозволів. Що більше агент може, то більший радіус ураження від помилкової дії й від ін'єкції в промпт. CLI без меж — це не автоматизація, а автоматизація ще й продакшн-інцидентів.

## То чи CLI — це кінцева точка?

Моя позиція однозначна: **термінал не є кінцевою точкою, і CLI не стане остаточним інтерфейсом для всіх.**

Коли агент переходить від однієї задачі за раз до одночасного ведення десятка довгих задач, самого терміналу швидко забракне. Потрібні черга задач, стан паралельних запусків, панель дозволів, перегляд diff, сповіщення й передавання між пристроями. Те, що OpenAI згодом зробила застосунок Codex, саме про це й свідчить: термінал добре пасує для запуску й виконання, але не конче для нагляду людини за цілою командою агентів.

CLI також не є найкращим протоколом для всіх інструментів. API й MCP мають чітку схему й зазвичай стабільніші, ніж парсинг логів природною мовою; а Computer Use відповідає за ту останню милю, де немає ні API, ні CLI.

Але CLI не зникне. Він радше стане «вузькою талією» у світі агентів: згори — IDE, десктопний застосунок, веб, телефон; знизу — Git, тести, бази даних, контейнери й хмарні сервіси; а передавання між ними всюди відбувається через команди й структуровані результати.

![](https://file1.kamacoder.com/i/web/2026-07-16_10-58-57.jpg)

Схема показує, чому CLI, навіть не бувши остаточним інтерфейсом, залишиться надовго. Майбутнє не належатиме одній точці входу: буде поділ на три шари — нагляд людини, оркестрація агентів, виконання інструментами; CLI на рівні виконання є найзрілішим каналом, але співіснуватиме з API, MCP і Computer Use.

Тож справжня кінцева точка — не CLI.

**Кінцева точка — це коли в кожної програми виростає інтерфейс, який агент може викликати, перевірити, проаудитувати й безпечно замкнути.**

CLI просто виявився готовим найпершим.
