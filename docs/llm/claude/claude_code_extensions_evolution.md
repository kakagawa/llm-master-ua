# Глибше про Claude Code: від CLAUDE.md до Hooks, Skills і субагентів

Сьогодні не про те, як налаштувати якусь окрему можливість Claude Code, а про те, як пов'язані чотири речі, що їх найлегше переплутати: `CLAUDE.md`, хуки, скіли, субагенти.

Раніше ми окремо розбирали, [як усе-таки писати CLAUDE.md](./claude_md.md), і розкладали [практичний досвід із Claude Skills](./claude_skills.md). Але після цього в багатьох лишається питання: **хіба все це не про те саме — задати Claude правила? Навіщо аж чотири механізми?**

Бо керують вони геть різними речами.

Запам'ятайте цю лінію розвитку:

**дати Claude запам'ятати правила → зробити так, щоб ключові дії гарантовано відбувалися → підвантажувати спеціалізовані здатності на вимогу → віддати складні задачі окремим ролям.**

Тобто:

`CLAUDE.md → Hooks → Skills → Subagents`

Зауважте: це не хронологія випуску чотирьох функцій, а **лінія зростання інженерної зрілості**. Кожен крок уперед виникає тому, що попередній шар не розв'язує нової проблеми.

![Розвиток Claude Code від постійних правил CLAUDE.md до керування подіями через хуки, здатностей на вимогу в скілах і окремих ролей у субагентах](https://file1.kamacoder.com/i/web/20260713152556_claude_code_extensions_01_evolution_compressed.png)

Схема показує, чому проєкт, що починався з кількох правил, зрештою обростає автоматичними перевірками, спеціалізованими процесами й кількома агентами. Пізніші можливості не замінюють ранніх — вони крок за кроком виносять «вимогу, написану для моделі» назовні, у контрольні точки, пакети здатностей і окремі одиниці виконання.

## Етап 1: спершу CLAUDE.md, щоб Claude знав, як тут працюють

Припустімо, ви доручаєте Claude Code змінити платіжний інтерфейс.

Щоразу доводиться переказувати те саме: у проєкті pnpm, суми скрізь у копійках, таблиці бази не чіпати напряму, після змін обов'язково прогнати тести.

Сказати це раз корисно — але лише для цієї розмови. Задача довшає, контекст стискається, і попередні вимоги можуть потонути.

Саме це й розв'язує `CLAUDE.md`. Він кладе стабільні між задачами знання про проєкт у постійний контекст:

```md
## Правила проєкту

- Використовуємо pnpm, не npm
- Суми зберігаємо в копійках, числа з рухомою комою заборонені
- Після змін у платіжному модулі запускати pnpm test:payment
- Не змінювати схему бази даних без підтвердження
```

Claude Code бачить це щоразу, коли заходить у проєкт, і перевиховувати його не треба. У корені пишуть глобальні обмеження, у підтеках додають правила модулів — дійшовши до відповідної теки, модель підвантажить конкретніший контекст.

Роль `CLAUDE.md` тут цілком зрозуміла: **це завжди активна інструкція до проєкту.**

Але він має дві межі, яких не обійти.

По-перше, **побачити не означає зробити.** «Після змін запускати тести» лишається інструкцією природною мовою, і зрештою модель має її запам'ятати, зрозуміти й виконати з власної ініціативи.

По-друге, **постійний контекст не безкоштовний склад.** Якщо запхати туди інструкцію з випуску, документацію до API і процедури розбору інцидентів, кожен раунд тягтиме з собою мішок наразі непотрібної інформації, а головне розмиватиметься.

Звідси й наступний шар: деякі речі не можна просто нагадувати — вони мусять автоматично відбуватися в потрібний момент.

## Етап 2: додаємо хуки, щоб «слід зробити» стало «спрацювало — зробилося»

Візьмімо ту саму справу: «після змін обов'язково прогнати перевірку».

Записане в `CLAUDE.md`, це означає: Claude, не забудь зробити.

Оформлене як хук, це означає: щойно редагування завершилося, ця контрольна точка спрацьовує.

Хуки вбудовуються в життєвий цикл Claude Code. Виклик інструмента не завершується просто тоді, коли модель вирішила, — усередині є низка подій, які можна перехоплювати й на які можна відповідати:

- `PreToolUse`: перед виконанням інструмента, можна перевірити, змінити або заблокувати виклик;
- `PostToolUse`: після успішного виконання, можна відформатувати, перевірити й повернути результат у контекст;
- `PostToolUseFailure`: після невдачі — записати помилку чи додати діагностику;
- `Stop`: коли Claude збирається завершувати, перевірити, чи задачу справді виконано;
- `SubagentStart`, `SubagentStop`: на старті й завершенні субагента додати обмеження або прийняти результат.

![Хуки вставляють контрольні точки до і після викликів інструментів у Claude Code та на прийманні, повертаючи агентові докази невдачі](https://file1.kamacoder.com/i/web/20260713152556_claude_code_extensions_02_hooks_loop_compressed.png)

Схема показує, куди саме в циклі агента вбудовуються хуки. Це не пояснювальна записка збоку від циклу, а ворота на вузлах «готуюся діяти», «дію завершено», «готуюся завершувати»; якщо умова не виконана, помилку чи доказ повертають Claude, щоб він виправляв далі.

Мінімальна перевірка після редагування виглядає приблизно так:

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "pnpm lint"
          }
        ]
      }
    ]
  }
}
```

Сучасні хуки вміють не лише запускати shell. Вони можуть викликати HTTP, інструменти MCP, а то й дати промпту чи тимчасовому агентові ухвалити рішення. Але хай як змінюється форма виконання, суть лишається та сама: **запуск відбувається за подією життєвого циклу, а не тоді, коли Claude про це згадає.**

Тільки не обожествляйте хуки.

Хуки пасують діям формату «щоразу, коли трапляється ця подія, треба зробити ось це»: форматування, блокування небезпечних команд, аудит. Вони не годяться для цілої інструкції з випуску, яка вимагає розуміння бізнесу й коригування кроків за обставинами.

**Детерміновані дії — хукам, процеси, що потребують міркування, у хуки не запихайте.**

## Етап 3: скіли, щоб винести спеціалізовані знання з постійного контексту

Проєкт розвивається, і ви натрапляєте на інший клас матеріалів:

- чекліст, потрібний лише під час випуску;
- runbook, потрібний лише під час розбору продакшн-інциденту;
- правила безпеки, потрібні лише під час рев'ю платіжного коду;
- опис полів і скрипти, потрібні лише під час роботи з певним внутрішнім API.

Це все важливе, але потрібне не в кожній задачі.

Запхати в `CLAUDE.md` — контекст дедалі роздуватиметься; оформити хуком — не вдасться виразити «спершу оцінити симптом, а потім обрати різні шляхи розбору». Ось тут і потрібен скіл.

Скіл — це **набір знань і робочих процесів, що завантажується на вимогу**. На старті Claude Code зазвичай бачить лише його назву й опис, а повний вміст підвантажує, коли вирішить, що той стосується поточної задачі:

```text
.claude/skills/payment-review/
├── SKILL.md
├── references/
│   ├── risk-rules.md
│   └── database-schema.md
├── scripts/
│   └── check-money-unit.sh
└── assets/
    └── review-template.md
```

Найважливіша тут не сама структура тек, а те, що **змінився спосіб завантаження контексту**.

`CLAUDE.md` — це «беремо щоразу»; скіл — «розгортаємо, коли знадобився». А `SKILL.md` може далі вказувати на довідки, скрипти й шаблони, щоб Claude читав саме той шматок, який зараз потрібен.

Це і є поступове розкриття. Про категорії скілів, написання description і накопичення розділу з пастками ми докладно говорили в статті [Claude Skills на практиці](./claude_skills.md), тож тут не повторюємося.

Тепер можна чітко розвести хуки й скіли:

- хук запускається подією й наголошує на тому, що **ця дія мусить відбутися**;
- скіл запускається викликом користувача чи наміром задачі й наголошує на тому, **як робляться справи цього класу**;
- хук — радше ворота, скіл — радше фаховий посібник;
- хук прагне стабільного повторення, скіл дозволяє Claude міркувати за обставинами.

Наприклад, хук `PostToolUse` може після зміни платіжного коду прогнати сканування одиниць виміру сум; а скіл `payment-review` пояснює Claude, як після виявлення проблеми оцінити ризик, дописати тести й запропонувати виправлення.

## Етап 4: субагенти, щоб «один Claude на все» перетворився на поділ ролей

Зі скілами Claude уже здобуває спеціалізовані здатності на вимогу. Але у складних задачах лишається ще одна, менш помітна проблема: **уся робота й далі тісниться в одному контексті.**

Головний агент спершу читає десятки файлів, щоб локалізувати проблему, потім змінює код, ганяє тести, а наприкінці ви ще й просите його перевірити власну реалізацію. Контекст дедалі бруднішає, ранні обмеження стискаються; а гірше те, що агент, який шукає помилки у власній відповіді, природно схильний себе схвалювати.

Субагенти розв'язують не задачу «додати ще один промпт», а задачу **відкрити ще один незалежний контекст виконання**.

Власного субагента можна описати так:

```md
---
name: payment-security-reviewer
description: Після змін у платіжному модулі незалежно перевіряє ризики щодо сум, прав доступу та ідемпотентності
tools: Read, Glob, Grep, Bash
model: sonnet
skills:
  - payment-review
---

Роби лише рев'ю безпеки, бізнес-код не змінюй. Висновок обов'язково має містити місце ризику, умову спрацювання й доказ перевірки.
```

Він має власний системний промпт, набір інструментів, модель, права, скіли й контекстне вікно. Головний агент лише делегує задачу й отримує підсумок — йому не треба тягти назад у головний потік ті десятки файлів і весь вивід команд, які читав субагент.

![Головний агент делегує задачі з тестів, безпеки й продуктивності субагентам з окремими контекстами й отримує лише висновки з доказами](https://file1.kamacoder.com/i/web/20260713152556_claude_code_extensions_03_subagent_isolation_compressed.png)

Схема показує, що саме економить окремий контекст. Три агенти — з тестів, безпеки й продуктивності — працюють кожен у чистому вікні, шум процесу лишається в їхніх контекстах, а до головного агента повертаються лише висновки з доказами; виконавець і рев'юер розділені структурно.

Тож скіл і субагент — теж різні речі:

- скіл — це «метод», який можна перевикористати;
- субагент — «роль», яка самостійно працює з цим методом;
- скіл завантажує вміст у поточний контекст;
- субагент виконує роботу в іншому контексті й повертає лише результат.

Їх можна й поєднувати. Агентові з безпеки заздалегідь дають скіл із безпеки, агентові з тестів — скіл із тестів, а головний агент ділить задачу, зводить висновки й вирішує, чи вносити подальші зміни.

Далі за цим кроком лежить складніша оркестрація, про яку ми говорили в [динамічних робочих процесах](./dynamic_workflows.md): кілька агентів паралельно, змагальна перевірка, генерація з відсівом. Але не біжіть туди одразу: якщо задачу зрозуміло описують дві ролі, не запускайте десять агентів заради солідності.

## Як обирати між чотирма шарами

Повернімося до найлегшої для плутанини ситуації: надійшла нова вимога — куди її записати?

![Визначення того, куди має потрапити вимога — у CLAUDE.md, хуки, скіли чи субагентів — за критеріями постійних знань, спрацювання за подією, спеціалізованого методу й ізоляції контексту](https://file1.kamacoder.com/i/web/20260713152556_claude_code_extensions_04_decision_compressed.png)

Схема показує, як крок за кроком визначитися за чотирма ознаками: чи це треба знати щоразу, чи це мусить статися автоматично, чи потрібне спеціалізоване міркування, чи потрібна ізоляція контексту. Це не вибір «один із чотирьох», а спосіб знайти основний шар, до якого вимога належить.

Запам'ятайте чотири питання:

| Питання | Куди записати | Типовий приклад |
|---|---|---|
| Чи має Claude знати це щоразу? | `CLAUDE.md` | Стек, структура тек, команди збірки, заборонені зони |
| Чи мусить це виконатися, щойно трапилася подія? | Hooks | Форматування, блокування небезпечних команд, аудит |
| Чи потрібен цей метод лише в задачах певного класу? | Skills | Випуск, рев'ю, розбір інцидентів, аналіз даних |
| Чи потрібні окремий контекст або окрема роль? | Subagents | Широкий пошук, незалежна перевірка безпеки, паралельні тести |

На тому самому платіжному модулі:

1. `CLAUDE.md` фіксує одиницю виміру сум, команди проєкту й заборонені дії з базою;
2. хук після зміни файлу запускає статичну перевірку, а перед небезпечною операцією блокує її;
3. скіл зберігає методику рев'ю платежів, правила ризику й скрипти перевірки;
4. субагенти окремо перевіряють безпеку, тести й продуктивність, а головний агент зводить докази.

Виявляється, ці чотири шари не конкурують, а керують чотирма різними місцями в роботі агента:

**що лежить у контексті, що перехоплюється в життєвому циклі, що підвантажується на вимогу задачі й кому віддається складна робота.**

## Чотири найчастіші пастки

**Перша: запхати все в CLAUDE.md.**

У результаті Claude не стає обізнанішим — він просто щораунду тягає на собі цілий склад матеріалів. Лишайте там довгострокові стабільні правила, а спеціалізовані знання переносьте у скіли.

**Друга: записувати заборони лише природною мовою.**

Якщо «не чіпай `.env`» — це червона лінія безпеки, не покладайтеся на слухняність моделі. Те, що можна перекрити правами й хуком `PreToolUse`, робіть жорсткою межею.

**Третя: заганяти складні судження в купу shell у хуку.**

Хук — це тригер, а не смітник для всієї бізнес-логіки. Якщо треба читати матеріали, порівнювати варіанти й коригувати кроки за обставинами — віддайте це скілу або спеціалізованому агентові.

**Четверта: щойно задача більшає, шалено плодити субагентів.**

Субагенти витрачають додаткові токени, а ще мають свою ціну: опис задачі може загубити інформацію, а зведення результатів — спотворити її. Ділити варто лише тоді, коли шуму в процесі справді багато, ролі справді слід ізолювати або роботу справді можна виконувати паралельно.

## Наостанок

Багато хто, налаштовуючи Claude Code, одразу копіює чужий «повний комплект»: кількасот рядків `CLAUDE.md`, кілька десятків хуків, десяток скілів і ще команда субагентів.

**Це надто важко й надто рано.**

Сказали те саме правило двічі — запишіть у `CLAUDE.md`; дія мусить відбуватися завжди — зробіть хук; процес копіюєте знову й знову — виростіть скіл; робота потребує окремого дослідження — віддайте субагентові.

Не будуйте систему за списком можливостей. **Дивіться, на якому шарі ви застрягли, і підсилюйте саме його.**
