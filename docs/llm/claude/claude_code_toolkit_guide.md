# Повний посібник із Claude Code: як користуватися CLAUDE.md, Skills, субагентами, MCP, Hooks і плагінами

Раніше ми розбирали [різницю між Claude Code і Claude.ai](../intro/ai-coding-three-layers.md): **модель відповідає за міркування, а ядро агента — за читання файлів, зміну коду, запуск команд і перевірку результату.**

Також окремо розглядали, [як усе-таки писати CLAUDE.md](./claude_md.md) і [як Claude Code розуміє велику кодову базу](./claude_code_large_codebase.md).

Але на цьому місці багатьох спиняє низка нових слів:

`CLAUDE.md`, Skills, субагенти, MCP, Hooks, плагіни — усе це «додає Claude Code можливостей», то навіщо аж шість механізмів?

І якщо в проєкті потрібні всі, що налаштовувати першим, а що потім?

Ця стаття не переказує документацію за списком функцій.

Спершу пояснимо, чому вони з'явилися, далі розберемо кожен окремо, а наприкінці зберемо всі шість в одному реальному проєкті.

![Огляд розширень Claude Code](https://file1.kamacoder.com/i/web/20260729153227_claude_code_toolkit_01_cover-compressed.jpg)

Схема показує: Claude Code ніколи не ставав сильнішим від «універсального промпта» — його сила в системі роботи з чітким поділом праці. Довгострокові правила, спеціалізовані процеси, окремі ролі, зовнішні можливості, автоматичні ворота й поширення в команді — кожен складник розв'язує свій клас задач.

## 1. Чому саме лише спілкування з Claude Code рано чи пізно розхитається

На початку роботи з Claude Code тимчасової балачки цілком досить.

«У цьому проєкті pnpm».

«Після змін прожене юніт-тести».

«Не чіпай базу напряму».

«Перед релізом пройди наш чекліст».

Проблема в тому, що реальний проєкт не обмежується трьома раундами.

Claude читає десятки файлів, ганяє купу команд, розбирається з падінням тестів, а ще й переживає стиснення контексту. **Сказане вами мимохідь тісниться в одному контексті з дедалі більшою кількістю нової інформації.**

У командній роботі ще гірше.

Правила, які ви проговорили Claude, доводиться переказувати наново іншому колезі, на іншому комп'ютері, в іншому проєкті.

![Тимчасові правила з чату тонуть у нових повідомленнях](https://file1.kamacoder.com/i/web/20260729153229_claude_code_toolkit_02_background-compressed.jpg)

Схема показує: **чат годиться, щоб висловити поточну задачу, але не втримає цілої інженерної системи.** Правила, що живуть лише в чаті, розмиваються на довгій задачі; досвід, що живе лише в особистій сесії, команда перевикористати не може.

Тож розширення Claude Code по суті відповідають на шість питань:

| Питання | Чим користуватися |
|---|---|
| Що треба знати щоразу, заходячи в проєкт? | `CLAUDE.md` |
| Яким методом робити задачі певного класу? | Skills |
| Яка робота потребує окремого контексту чи окремої ролі? | Субагенти |
| Як звертатися до систем і даних поза репозиторієм? | MCP |
| Які дії мусять виконуватися, щойно трапилася подія? | Hooks |
| Як передати весь цей набір іншим проєктам і колегам? | Плагіни |

Запам'ятайте одне речення:

**CLAUDE.md відповідає за постійні правила, скіл — за метод на вимогу, субагент — за самостійну роботу, MCP — за зовнішні підключення, хук — за детерміновані дії, плагін — за пакування й поширення.**

Далі розберемо кожен.

## 2. CLAUDE.md: спершу дайте Claude знати, як тут працюють

### 2.1. Що таке CLAUDE.md

`CLAUDE.md` — файл із описом проєкту, який Claude Code читає автоматично.

Сюди пасує **стабільна, довгострокова інформація, потрібна майже в кожній задачі**:

- який стек у проєкті;
- команди збірки, тестування, форматування;
- ключові теки й межі модулів;
- стандарти коду й домовленості про іменування;
- які файли чіпати не можна;
- пастки, на які команда вже наступала й може наступити знову.

Сприймайте його як «інструкцію на перший день» для нового учасника.

README пишеться для людини, і головне в ньому — що це за проєкт і як його запустити.

`CLAUDE.md` пишеться для агента, і головне в ньому — **як діяти, отримавши задачу**.

![CLAUDE.md як інструкція до проєкту](https://file1.kamacoder.com/i/web/20260729153231_claude_code_toolkit_03_claude_md-compressed.jpg)

Схема показує: довгострокові правила не мають триматися на усних нагадуваннях програміста. Запишіть команди, архітектуру й заборонені зони в інструкцію — і Claude щоразу матиме стабільну відправну точку.

### 2.2. Де лежить CLAUDE.md

Чотири найуживаніші розташування:

| Розташування | Зона дії | Що туди класти |
|---|---|---|
| `~/.claude/CLAUDE.md` | Усі проєкти на вашій машині | Особисті вподобання й робочі звички |
| `корінь проєкту/CLAUDE.md` | Поточний проєкт, спільне для команди | Стек, команди, глобальні правила |
| `корінь проєкту/CLAUDE.local.md` | Поточний проєкт, лише для вас | Локальні адреси, особисті звички тестування |
| `якась підтека/CLAUDE.md` | Завантажується на вимогу під час роботи з модулем | Команди модуля, локальна архітектура й заборони |

Файл рівня проєкту варто комітити в Git.

`CLAUDE.local.md` зазвичай додають у `.gitignore` — не розсилайте всій команді інформацію про своє локальне середовище.

У великому репозиторії не запихайте правила всіх модулів у кореневий файл. Корінь — про глобальне, а фронтенд, платежі, дані тощо мають власні `CLAUDE.md`.

### 2.3. Як писати CLAUDE.md

Почніть із мінімальної версії:

```md
## Project instructions

## Commands

- Install: `pnpm install`
- Test: `pnpm test`
- Build: `pnpm build`

## Architecture

- `apps/web/` is the frontend.
- `services/api/` is the API service.
- Shared types live in `packages/types/`.

## Rules

- Use pnpm, never npm.
- Add tests for every bug fix.
- Do not edit generated files under `dist/`.
- Never run database migrations without explicit approval.
```

Щоб зрозуміти, чи вартий запис місця у файлі, поставте три питання:

1. чи знадобиться це ще не раз?
2. чи змінить це дії Claude?
3. чи варте воно того, щоб займати контекст у кожній сесії?

Три «так» — пишемо.

Чекліст релізу, кроки рев'ю безпеки, кількадесят сторінок документації API запихати сюди не треба. Це робота для скіла.

### 2.4. CLAUDE.md не є межею безпеки

Це важливо.

`CLAUDE.md` — настанова щодо поведінки, а не примусовий виконавець.

Запис «не виконуй небезпечних команд» знижує ймовірність помилки, але абсолютної гарантії не дає.

**Те, що справді треба заблокувати, віддавайте налаштуванням прав або хуку `PreToolUse`.**

Якщо Claude не дотримується правил, спершу запустіть `/memory` і переконайтеся, що файл узагалі завантажився, а далі перевірте, чи не є правила надто розмитими, задовгими або суперечливими.

Докладніший розбір — у статті [CLAUDE.md: пам'ять проєкту й керування контекстом](./claude_md.md).

## 3. Skills: перетворити повторювані методи на набір інструментів на вимогу

### 3.1. Яку задачу розв'язує скіл

Припустімо, у команди є процес релізу:

1. перевірити робочу копію;
2. прогнати тести;
3. згенерувати опис змін;
4. перевірити зміни в базі даних;
5. дати план відкату.

Процес важливий, але коли ви пишете звичайний бізнес-код, він вам не потрібен.

Якщо запхати його в `CLAUDE.md`, Claude тягатиме його в кожній сесії.

**Цінність скіла в тому, що спеціалізовані знання й процеси завантажуються лише тоді, коли з'явилася відповідна задача.**

Ви можете викликати його самі через `/skill-name`, а може й Claude вирішити це сам за полем `description`.

![Claude Code завантажує скіл на вимогу](https://file1.kamacoder.com/i/web/20260729153233_claude_code_toolkit_04_skills-compressed.jpg)

Схема показує: скіл — це не звалити всі матеріали на стіл назавжди, а взяти саме ту скриньку інструментів, яка потрібна для релізу, рев'ю чи розбору інциденту.

### 3.2. Як виглядає скіл

Скіл рівня проєкту лежить тут:

```text
.claude/skills/release-check/
├── SKILL.md
├── checklist.md
└── scripts/
    └── verify.sh
```

`SKILL.md` є точкою входу:

```md
---
name: release-check
description: Check whether the current changes are ready for release. Use for release preparation, pre-deployment review, or rollback planning.
disable-model-invocation: true
---

## Release check

1. Read `checklist.md`.
2. Inspect the current git diff.
3. Run `scripts/verify.sh`.
4. Report blockers, risks, and rollback steps.

Do not deploy. Only produce a release-readiness report.
```

Кілька ключових моментів:

- `description` — це не рекламний опис для людини, а вказівка Claude, **коли цей скіл завантажувати**;
- `disable-model-invocation: true` означає, що викликати його може лише користувач;
- великі довідкові матеріали виносять в окремі файли, а `SKILL.md` лишається входом і навігацією;
- скрипти роблять детерміновані перевірки, а Claude пояснює результат з огляду на обставини.

Виклик:

```text
/release-check
```

Особисті універсальні скіли можна класти в `~/.claude/skills/`, а спільні для проєкту — у `.claude/skills/`.

### 3.3. Коли варто робити скіл

Найпрактичніший сигнал — не «ці знання складні», а:

- той самий опис ви скопіювали вже втретє;
- якийсь розділ `CLAUDE.md` дедалі більше нагадує інструкцію з експлуатації;
- задача має фіксовані вхід, кроки й формат виводу;
- цей метод потребує шаблонів, прикладів або скриптів;
- одні й ті самі знання перевикористовують кілька ролей.

Скілів не має бути якомога більше.

Надто широкий опис призводить до спрацювань у нерелевантних задачах, а завеликий вміст після завантаження так само тисне на контекст.

Про категорії скілів, поступове розкриття й командну практику читайте в статті [Claude Skills на практиці](./claude_skills.md).

## 4. Субагенти: віддати складну роботу окремій ролі

### 4.1. Навіщо субагент, якщо є скіл

Скіл додає поточному агентові метод, але робота однаково відбувається **в поточному контексті**.

Рев'ю безпеки, дослідження всього репозиторію, розбір тестів читають багато файлів і породжують багато проміжного виводу.

Якщо запхати все це в головну сесію, її контекст швидко забруднюється.

Гірше того: агент, який писав код і потім сам його перевіряє, легко доходить висновку «я ж уже виправив, отже, проблем немає».

Цінність субагента в тому, що **відкривається окремий контекст, спеціалізована роль виконує задачу й повертає лише висновки з доказами.**

![Поділ праці між субагентами Claude Code](https://file1.kamacoder.com/i/web/20260729153234_claude_code_toolkit_05_subagents-compressed.jpg)

Схема показує: дослідження, тестування й рев'ю можуть виконувати окремі ролі. Шум процесу лишається в їхніх контекстах, а головний агент отримує лише підкріплені доказами результати.

### 4.2. Як створити субагента

Субагенти рівня проєкту лежать у `.claude/agents/`:

```md
---
name: security-reviewer
description: Review code changes for authentication, authorization, injection, secret exposure, and unsafe data handling.
tools: Read, Grep, Glob, Bash
model: inherit
skills:
  - secure-coding
---

You are an independent security reviewer.

Review changes without modifying business code.

For every finding, report:

1. file and location;
2. trigger condition;
3. impact;
4. evidence;
5. recommended fix.

If no issue is found, list what you checked. Do not return only "looks good".
```

Скористатися можна просто так:

```text
Хай security-reviewer незалежно перевірить ці зміни в модулі логіну й поверне лише висновки з доказами.
```

Або запустити `/agents`, щоб переглянути й налаштувати їх.

### 4.3. Які задачі варто віддавати субагентові

У придатних для цього задач зазвичай є спільна риса: **процес довгий, а головній сесії потрібен лише результат.**

Наприклад:

- дослідження великої кодової бази лише для читання;
- незалежна перевірка безпеки, продуктивності чи тестів;
- паралельне вивчення кількох незалежних модулів;
- потреба, щоб інша роль шукала помилки з протилежного погляду;
- бажання обмежити для ролі інструменти, модель або права.

Коли ділити не варто, теж очевидно:

- дрібна зміна в одному файлі;
- сильна залежність від великої кількості неявної інформації в головній сесії;
- підзадачі, що постійно чекають одна на одну;
- поділ коштує дорожче за саму задачу.

**Скіл — це метод, а субагент — роль, яка з цим методом працює самостійно.**

Їх можна поєднувати: у полі `skills` субагента заздалегідь підвантажити стандарти безпеки чи методику тестування.

## 5. MCP: під'єднати Claude Code до світу поза репозиторієм

### 5.1. Що таке MCP

Вбудовані файлові й термінальні інструменти Claude Code добре працюють із поточною робочою копією.

Але в реальній розробці потрібен доступ і до багатьох зовнішніх систем:

- GitHub чи інша платформа хостингу коду;
- трекери тікетів на кшталт Jira чи Linear;
- Sentry й платформи логування;
- бази даних і сховища даних;
- внутрішня документація, платформи релізів і бізнес-адмінки;
- браузер чи інструменти дизайну.

MCP, тобто Model Context Protocol, розв'язує питання, **як AI-застосунок єдиним способом знаходить і викликає зовнішні інструменти й дані**.

Вам не треба писати окрему інтеграцію під кожного агента.

Сервер MCP надає можливості, а Claude Code як клієнт MCP під'єднується й викликає їх.

![Claude Code під'єднується до зовнішніх систем через MCP](https://file1.kamacoder.com/i/web/20260729153236_claude_code_toolkit_06_mcp-compressed.jpg)

Схема показує: MCP — це керований перехідник, що дає Claude Code дотягнутися до платформ коду, баз даних і браузера поза репозиторієм; а ключі від доступу однаково мають лишатися в людини й у системних політиках.

### 5.2. Як додати сервер MCP

Додати віддалений сервер по HTTP:

```bash
claude mcp add --transport http issue-tracker https://mcp.example.com/mcp
```

Додати локальний сервер через stdio:

```bash
claude mcp add --transport stdio my-tools -- node ./tools/mcp-server.js
```

Корисні команди перевірки:

```bash
claude mcp list
claude mcp get issue-tracker
```

Усередині Claude Code стан під'єднання й автентифікації показує `/mcp`.

Спільну для команди конфігурацію MCP рівня проєкту можна записати в `.mcp.json`. Конфігурацію, витягнуту з репозиторію, треба перевірити й схвалити — файл у Git ще не означає, що він безпечний.

### 5.3. Найчастіші пастки MCP

**Перша: забагато прав.**

Для запитів до бази беріть обліковий запис лише для читання, не давайте одразу право на запис у продакшн.

Для рев'ю коду потрібне читання PR — не додавайте до нього заразом право видаляти репозиторій.

**Друга: забагато інструментів.**

Під'єднати за раз кілька десятків серверів і виставити кількасот інструментів означає ускладнити вибір і забруднити контекст.

Спершу під'єднайте найуживаніші можливості з найчистішим форматом результату.

**Третя: сприймати MCP як методику роботи.**

MCP відповідає лише за те, «щоб можна було під'єднатися й викликати».

А що саме запитувати, як оцінювати й у якому форматі віддавати — це справа `CLAUDE.md`, скіла чи субагента.

Тож найтиповіше поєднання таке:

**MCP дає руки й очі, скіл дає метод роботи.**

Щоб заглибитися в сам протокол, читайте [Протокол MCP](../app/mcp_protocol.md).

## 6. Hooks: щоб ключові дії більше не залежали від «не забути»

### 6.1. Чим хук відрізняється від нагадування Claude

Ви пишете в `CLAUDE.md`:

«Після кожної зміни файлів запускай форматування».

Це нагадування.

Ви налаштовуєте хук `PostToolUse`, щоб після успішного редагування автоматично запускалася команда форматування.

Це детермінована дія.

Хуки спрацьовують на певних подіях життєвого циклу Claude Code, наприклад:

- на старті сесії підкласти інформацію про середовище;
- перед виконанням інструмента перевірити чи заблокувати;
- після зміни файлу автоматично відформатувати;
- після невдачі інструмента записати діагностику;
- надіслати сповіщення на десктоп, коли Claude чекає підтвердження;
- зберегти важливий стан перед стисненням контексту.

![Hooks як автоматичні ворота в Claude Code](https://file1.kamacoder.com/i/web/20260729153237_claude_code_toolkit_07_hooks-compressed.jpg)

Схема показує: форматування, тести й перевірка небезпечних команд не мають триматися на тому, що хтось нагадає. Хук — як автоматичні ворота: подія трапилася — дія виконалася, що має пройти — проходить, що треба спинити — спиняється.

### 6.2. Як налаштувати хук

Хуки зазвичай описують у `.claude/settings.json` або в `~/.claude/settings.json` на рівні користувача.

Ось приклад, який запускає форматування після того, як Claude застосував `Edit` чи `Write`:

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write"
          }
        ]
      }
    ]
  }
}
```

Після налаштування запустіть `/hooks` і перевірте, чи завантажилися подія, матчер і команда.

У реальному проєкті складну логіку краще винести в окремий скрипт:

```json
{
  "type": "command",
  "command": ".claude/hooks/check-edited-file.sh"
}
```

Тоді скрипт можна покласти в Git, окремо протестувати й не запихати довгий shell у JSON.

### 6.3. Як користуватися хуками, щоб вони не стали новою пасткою

Хук виконується автоматично, тож обережності потрібно більше, ніж зі звичайним промптом.

- звужуйте зону збігу, не ставте `.*` на всі події;
- за замовчуванням виконуйте швидко, не блокуйте кожне редагування важкими задачами;
- у скрипта мають бути зрозумілі коди виходу й повідомлення про помилки;
- не робіть у хуку потай високоризикових дій — релізів, видалень, пушів;
- спершу запустіть скрипт вручну, а вже тоді підключайте його як хук;
- для складних суджень беріть скіл чи окремого агента-рев'юера, а не купу shell.

Найкраще хуку пасують дії формату «дійшло сюди — мусить виконатися».

Найгірше — відкриті питання, що потребують прочитати багато контексту й зважити кілька варіантів.

## 7. Плагіни: перетворити набір можливостей на продукт, який команда встановлює

### 7.1. Плагін не є сьомою можливістю

Багато хто сприймає плагін як «ще один інструмент».

Насправді це радше **формат пакування й поширення**.

Один плагін може одразу містити:

- скіли;
- субагентів;
- хуки;
- конфігурацію серверів MCP;
- конфігурацію LSP;
- інші повторно вживані компоненти.

Експериментувати в теці `.claude/` одного проєкту зручно для швидких ітерацій.

А коли конфігурація вже стабільна й потрібні встановлення, оновлення й версіювання між проєктами й командами — робіть із неї плагін.

![Поширення плагінів Claude Code у команді](https://file1.kamacoder.com/i/web/20260729153239_claude_code_toolkit_08_plugins-compressed.jpg)

Схема показує: плагін складає розрізнені скіли, агентів, хуки й конфігурацію MCP в один командний набір інструментів. Підтримує одна людина, користуються всі — і нікому не доводиться налаштовувати все руками на кожному комп'ютері.

### 7.2. Як установити плагін

У Claude Code введіть:

```text
/plugin
```

Відкриється панель плагінів, де їх можна переглядати, встановлювати й налаштовувати.

Установлення плагіна з офіційного маркетплейсу:

```text
/plugin install github@claude-plugins-official
```

Спершу подивіться, які компоненти дає плагін, які права йому потрібні й до яких зовнішніх систем він під'єднується.

Установлення плагіна не означає видачі йому необмежених повноважень.

### 7.3. Як виглядає власний плагін

Мінімальна структура може бути такою:

```text
team-toolkit/
├── .claude-plugin/
│   └── plugin.json
├── skills/
│   └── release-check/
│       └── SKILL.md
├── agents/
│   └── security-reviewer.md
├── hooks/
│   └── hooks.json
└── .mcp.json
```

`plugin.json` описує сам плагін:

```json
{
  "name": "team-toolkit",
  "description": "Shared release and review workflows for our engineering team",
  "version": "1.0.0"
}
```

Під час локальної розробки його можна підключити через `--plugin-dir`:

```bash
claude --plugin-dir ./team-toolkit
```

Спершу доведіть компоненти до стабільної роботи в одному-двох проєктах, а вже тоді публікуйте в командному маркетплейсі.

**Плагін розв'язує задачу поширення, але він не виправить поганого скіла, надто широкого хука чи MCP із завеликими правами всередині себе.**

## 8. Як поєднати всі шість: приклад реального проєкту

Припустімо, ви додаєте в систему електронної комерції функцію «погодження повернення коштів».

Вона зачіпає бізнес-правила, базу даних, права доступу, тести, тікети й реліз.

Правильний підхід — не запхати всі вимоги в один суперпромпт, а розкласти їх по шарах.

### 8.1. CLAUDE.md: стабільні факти, потрібні щоразу

```md
- Money is stored in cents as integer values.
- Refund APIs must be idempotent.
- All approval actions require an audit log.
- Run `pnpm test:payments` after changing the payment module.
- Never run production migrations without explicit approval.
```

Ці правила не залежать від конкретної задачі — їх має знати будь-яка зміна в платежах.

### 8.2. Скіл: методика рев'ю повернень

Створюємо скіл `refund-review`, у якому лежать:

- чекліст ідемпотентності;
- правила щодо точності сум;
- опис машини станів погодження;
- вимоги до полів аудиту;
- шаблони тестів;
- формат підсумкового звіту.

Надалі, працюючи з поверненнями, не доведеться щоразу копіювати кілька десятків рядків вимог.

### 8.3. Субагент: незалежна перевірка безпеки

Хай `payment-security-reviewer` у режимі лише для читання перевіряє:

- чи можна погодити повернення без потрібних прав;
- чи не призведе повтор запиту до подвійного повернення коштів;
- чи не витікають у логи чутливі дані;
- чи не можна обійти перехід станів;
- чи є тести з доказами.

Головний агент у його міркуваннях не бере участі — він отримує лише висновок і вирішує, що змінювати.

### 8.4. MCP: підключення до справжніх інженерних систем

Через MCP можна:

- прочитати тікет про повернення;
- пошукати історичні аномалії на платформі помилок;
- переглянути PR на платформі хостингу коду;
- зробити запит до даних тестового середовища обліковим записом лише для читання.

Підключення дає доступ до справжньої інформації, а правила оцінювання й далі беруться з опису проєкту та скіла.

### 8.5. Hooks: автоматичні жорсткі перевірки

- після зміни платіжного коду автоматично запускати форматування й статичне сканування;
- перед виконанням команд бази даних перевіряти середовище;
- перед комітом перевіряти, чи пройшли ключові тести;
- надсилати розробнику сповіщення, коли Claude чекає погодження.

Не варто сподіватися, що агент «сам щоразу згадає».

### 8.6. Плагін: віддати готове рішення всій команді

Коли скіл повернень, субагент із безпеки, хуки й конфігурація MCP працюють стабільно, пакуємо їх у плагін `payment-engineering`.

Новий колега після встановлення отримує той самий набір можливостей, а не чийсь досвід, переказаний із вуст в уста.

Тепер зв'язок шести шарів очевидний:

```text
CLAUDE.md: як у цьому проєкті працюють постійно
Skill: як конкретно робити задачі цього класу
Subagent: кому доручити виконання окремо
MCP: як під'єднати цій ролі зовнішні інструменти й дані
Hook: де автоматично перевірити й перехопити
Plugin: як запакувати всі попередні шари для команди
```

## 9. У якому порядку налаштовувати з нуля

Не встановлюйте в перший же день кілька десятків плагінів, не під'єднуйте десяток MCP і не запускайте команду субагентів.

Що більше конфігурації, то більше конфліктів, проблем із правами й витрат контексту.

Раджу йти за порядком виникнення проблем.

### Крок 1: доведіть кореневий CLAUDE.md до робочого стану

Опишіть лише команди, архітектуру, заборонені зони й найпоширеніші пастки.

Запустіть `/memory` і переконайтеся, що файл завантажився.

### Крок 2: оформте повторюваний процес як скіл

Почніть із того процесу релізу, рев'ю чи розбору інцидентів, який копіюєте найчастіше.

Запустіть `/skills` і перевірте опис та зону дії.

### Крок 3: додайте хук для дій, які мусять відбуватися

Спершу підключіть детерміноване: форматування, lint, блокування небезпечних команд.

Запустіть `/hooks`, перевірте конфігурацію й прожене вручну сценарії успіху й невдачі.

### Крок 4: створюйте субагентів лише для чітких сценаріїв

Насамперед для рев'ю безпеки або широкого дослідження лише для читання.

Запустіть `/agents` і перевірте, які в них доступні інструменти, моделі та скіли.

### Крок 5: під'єднуйте MCP за реальною потребою

Спершу одна система, якою ви користуєтеся часто, і мінімальні права.

Запустіть `/mcp` і подивіться стан автентифікації й під'єднання.

### Крок 6: плагін робіть, коли все стабілізувалося

Спершу доведіть, що цей набір справді корисний у проєкті, а вже тоді думайте про поширення між проєктами.

Зарання зроблений плагін лише швидше розтиражує конфігурацію, яку ще не продумали.

Якщо конфігурація не діє, можна ще запустити:

```text
/doctor
/status
/permissions
```

Спершу з'ясуйте, «чи завантажилося, звідки завантажилося і які зрештою права», а вже потім підозрюйте модель.

## 10. Шість найчастіших помилок у налаштуванні

### 10.1. Перетворити CLAUDE.md на енциклопедію

Проблема: він займає контекст щораунду, а справді важливі правила не виділяються.

Як лікувати: лишити стабільні факти, спеціалізовані процеси перенести у скіли, довгі матеріали підвантажувати на вимогу.

### 10.2. Надто розмитий description у скіла

Проблема: опис на кшталт «допомагає в розробці» збігається з усім, а отже, не означає нічого.

Як лікувати: чітко описати задачу, контекст спрацювання й те, коли скіл не застосовується.

### 10.3. Плодити субагентів заради «паралельності»

Проблема: поділ задачі, передавання контексту і зведення результатів теж коштують.

Як лікувати: ділити лише тоді, коли задача справді виконується самостійно або шум процесу справді треба ізолювати.

### 10.4. Одразу давати MCP право запису в продакшн

Проблема: разом із зоною під'єднання розширюється й радіус ураження від помилки.

Як лікувати: спершу лише читання, мінімальні права, а чутливі дії лишати на ручне підтвердження.

### 10.5. Робити хук важким і широким

Проблема: кожне редагування підвисає, ще й може спрацьовувати на нерелевантних файлах.

Як лікувати: звузити matcher, складну логіку винести в тестований скрипт, а важкі задачі перевести у скіл на вимогу.

### 10.6. Вважати, що чим більше плагінів, то сильніше

Проблема: компоненти можуть конфліктувати, список інструментів роздувається, а джерела прав стає важко аудитувати.

Як лікувати: ставити лише ті плагіни, що розв'язують конкретну проблему, і періодично перевіряти їхнє походження діагностичними командами.

## 11. Кілька частих питань

### Чим CLAUDE.md відрізняється від автоматичної пам'яті?

`CLAUDE.md` — це правила проєкту, які команда свідомо підтримує: їх можна комітити в Git і виносити на рев'ю.

Автоматична пам'ять — це досвід, який Claude накопичує на цій машині під час роботи; вона добре зберігає знахідки з налагодження й особисті звички.

Командні домовленості пишіть у `CLAUDE.md`, не чекайте, доки автоматична пам'ять їх угадає.

### Скіл чи хук?

Треба врахувати контекст і виконати цілу методику — скіл.

Треба, щоб дія гарантовано виконувалася за подією й давала стабільний перевірюваний результат, — хук.

Наприклад, «зробити рев'ю PR за командними стандартами» — це скіл, а «автоматично форматувати після редагування» — хук.

### Скіл чи субагент?

Треба додати знань у поточний контекст — скіл.

Треба винести довгий процес назовні й отримати лише результат — субагент.

Якщо ролі з безпеки потрібна стала методика перевірки, нехай субагент заздалегідь підвантажує відповідний скіл.

### Як пов'язані MCP і плагін?

MCP — протокол під'єднання, що розв'язує питання «як Claude викликає зовнішню систему».

Плагін — пакет поширення, що розв'язує питання «як передати іншим конфігурацію MCP разом зі скілами, агентами й хуками».

### Чи справді краще, коли налаштовано всі шість?

Не обов'язково.

Ці можливості — не відзнаки рівня.

Маленькому проєкту може вистачити 30 рядків `CLAUDE.md` і одного хука для форматування. Скіл додають, коли з'явився повторюваний процес; субагента — коли контекст справді треба ізолювати; MCP — коли можливості поза репозиторієм справді потрібні.

**Найкраща конфігурація Claude Code — не та, де найбільше компонентів, а та, де кожен шар розв'язує справжню проблему.**
