# Протокол MCP: новий стандарт виклику інструментів агентами

У попередній статті ми розглядали, що [дизайн інструментів визначає стелю агента](./agent_tool_design.md).

Суть в одному реченні: **інструменти — це не перелік API, а межі дій агента.**

Опис, схема параметрів, формат відповіді, межі прав, відновлення після помилок — якщо це спроєктовано погано, агент неодмінно збиватиметься.

Але тут виникає наступне питання:

«Якщо кожен інструмент доводиться підключати окремо, то для різних інструментів, різних продуктів і різних моделей ми щоразу винаходитимемо велосипед?»

Саме так.

І це та проблема, яку розв'язує MCP.

Найбільша біда багатьох проєктів з агентами зараз не в тому, що модель не вміє викликати інструменти, а в тому, що підключення інструментів украй розпорошене.

Підключити GitHub — окремий код.

Підключити базу даних — окремий код.

Підключити локальні файли — окремий код.

Підключити Slack, Notion, Jira, Sentry — і знову щоразу окремо.

Сьогодні підключаємо це для одного застосунку, завтра для іншого, післязавтра для внутрішнього агента компанії.

І що далі, то більше це схоже на роботу з клеєм.

Тож поговорімо про річ, яку дедалі частіше питають на співбесідах про агентів:

**MCP, Model Context Protocol.**

Спершу зрозумійте це так:

**MCP — це стандартний протокол, за яким AI-застосунки уніфіковано підключаються до зовнішніх інструментів, даних і шаблонів промптів.**

Зверніть увагу: це не модель.

І не фреймворк агентів.

Це радше «протокол підключення інструментів» епохи агентів.

![Яку проблему розв'язує MCP: не змушувати кожен AI-застосунок наново підключати кожен інструмент](https://file1.kamacoder.com/i/web/20260520112737_mcp_protocol_01_integration_problem_compressed.png)

## 1. Чому взагалі з'явився MCP

Не поспішаймо із заучуванням архітектури.

Спершу подивімося, як виглядає світ без MCP.

Припустімо, ви робите помічника для програмування, який має вміти:

- читати локальні файли;
- шукати issue на GitHub;
- запитувати базу даних;
- дивитися помилки в Sentry;
- надсилати повідомлення у Slack;
- читати корпоративну базу знань.

Без єдиного протоколу для кожної системи доводиться вигадувати власний формат інструментів:

- як виявляти інструменти?
- як описувати схему параметрів?
- як їх викликати?
- як повертати результат?
- як контролювати права?
- як спілкуватися локальним і віддаленим інструментам?
- як клієнт дізнається, що інструменти змінилися?

Якщо кожен продукт розв'язує це самотужки, виходить хаос.

Постачальникам інструментів теж боляче.

Скажімо, ви зробили інструмент для запитів до бази даних.

Хочете, щоб ним могли користуватися Claude Desktop.

І Cursor.

І AI-розширення у VS Code.

І внутрішній агент компанії.

Невже писати окремий плагін під кожен хост?

Це надто марнотратно.

Ідея MCP така:

**постачальник інструментів надає можливості за стандартом MCP, а AI-застосунок за тим самим стандартом до них підключається.**

Так між інструментами й AI-застосунками з'являється спільний шар протоколу.

Як HTTP API між фронтендом і бекендом.

Як єдиний протокол між клієнтом і базою даних.

MCP розв'язує не питання «як модель міркує».

Він розв'язує: **як AI-застосунок стандартизовано отримує контекст, викликає інструменти й використовує шаблони промптів.**

## 2. MCP не є заміною Function Calling

Почувши про MCP уперше, багато хто змішує його з Function Calling.

Вони пов'язані, але це різні речі.

Function Calling розв'язує:

**чи треба в цій відповіді моделі викликати певну функцію і з якими параметрами.**

Це ближче до рівня виклику моделі.

Скажімо, ви надіслали моделі визначення інструментів, і вона повертає:

```json
{
  "name": "get_order_detail",
  "arguments": {
    "order_id": "202605200001"
  }
}
```

Потім ваша програма виконує цю функцію й повертає результат моделі.

Це Function Calling.

MCP розв'язує зовсім інший рівень:

**звідки ці інструменти беруться? як їх виявити? як підключитися? як спілкуватися? як надати їх різним AI-застосункам?**

Тобто Function Calling — це радше «формат одного виклику між моделлю й інструментом».

А MCP — «протокол з'єднання між AI-застосунком і сервером інструментів».

Розуміти можна так:

**Function Calling — про те, як модель викликає інструмент.**

**MCP — про те, як інструмент стандартизовано підключається до AI-застосунку.**

Вони не взаємовиключні.

Багато AI-застосунків спершу виявляють інструменти через MCP, а потім перетворюють їх на формат Function Calling / Tool Use, зрозумілий моделі, щоб вона обрала потрібний.

![Зв'язок MCP і Function Calling: один відповідає за підключення інструментів, другий — за виклик моделлю](https://file1.kamacoder.com/i/web/20260520112738_mcp_protocol_02_fc_relation_compressed.png)

Це найчастіше питання на співбесідах.

Якщо інтерв'юер питає:

«Чим MCP відрізняється від Function Calling?»

Не відповідайте:

«MCP просунутіший».

Це порожньо.

Скажіть так:

> «Function Calling — це механізм виклику інструментів на боці моделі: важливо, яку функцію й з якими параметрами модель видає. MCP — це протокол підключення інструментів на боці застосунку: важливо, як AI-застосунок виявляє, підключає й викликає зовнішні інструменти, ресурси та шаблони промптів. У реальній системі MCP може бути джерелом інструментів, а Function Calling — способом, яким модель їх обирає й викликає».

Така відповідь надійна.

## 3. Основна архітектура MCP: Host, Client, Server

В офіційній архітектурі MCP є три ролі:

**Host, Client, Server.**

Їх обов'язково треба розрізняти.

Інакше в розмові про MCP легко заплутатися.

### 1. Host: сам AI-застосунок

Host — це застосунок, яким реально користується людина.

Наприклад:

- Claude Desktop;
- Claude Code;
- AI-розширення у VS Code;
- помічники для коду на кшталт Cursor;
- власна агентна платформа компанії.

Host відповідає за взаємодію з користувачем, виклик моделі, рішення щодо прав і зведення контексту.

Простими словами, Host — це оболонка, у якій живе «мозок».

Користувач не спілкується з MCP Server напряму.

Користувач ставить питання в Host.

### 2. Client: компонент усередині Host, що з'єднується з конкретним Server

MCP Client — це не окремий продукт.

Це зазвичай компонент з'єднання всередині Host.

Один Host може підключатися до кількох MCP Server.

На кожне підключення в Host зазвичай створюється відповідний Client.

Тож обов'язки Client такі:

- встановити з'єднання з конкретним MCP Server;
- узгодити версію протоколу й можливості;
- надіслати запит на перелік інструментів;
- надіслати запит на виклик інструмента;
- приймати результати й сповіщення;
- підтримувати межі безпеки цього з'єднання.

Розуміти можна так:

**один MCP Client — це канал з'єднання з одним MCP Server.**

### 3. Server: надає інструменти, ресурси й шаблони промптів

MCP Server — це та сторона, що справді надає можливості.

Наприклад:

- Server файлової системи: читання файлів, перелік каталогів;
- Server GitHub: issue, PR, репозиторії;
- Server бази даних: схема, інструменти запитів;
- Server Sentry: події помилок і моніторинг;
- внутрішній Server компанії: замовлення, заявки, база знань, платформа логів.

Server не спілкується з користувачем.

Server лише надає можливості за протоколом MCP.

Цих можливостей три типи:

**Tools, Resources, Prompts.**

Про них — далі окремо.

![Основна архітектура MCP: Host керує застосунком, Client — з'єднанням, Server надає можливості](https://file1.kamacoder.com/i/web/20260520112740_mcp_protocol_03_host_client_server_compressed.png)

Найбільша перевага цієї архітектури — ізоляція.

Один Host може підключати кілька Server.

Але кожен Server не має бачити всю розмову й не має довільно звертатися до даних інших Server.

Host централізовано керує правами й контекстом.

Server надає лише те, що має надавати.

Це дуже важливо.

MCP не про те, щоб усі інструменти бачили одне одного.

**MCP про те, щоб Host міг комбінувати кілька серверів інструментів у керованих межах.**

## 4. У MCP два рівні: рівень даних і транспортний рівень

Багато хто, розповідаючи про MCP, обмежується фразою «він уміє підключати інструменти».

Це надто поверхово.

У MCP треба розуміти щонайменше два рівні: **рівень даних** і **транспортний рівень**.

### 1. Рівень даних: визначає повідомлення й семантику

Рівень даних відповідає за те:

- як відбувається ініціалізація;
- як узгоджуються можливості;
- як перелічуються інструменти;
- як викликаються інструменти;
- як читаються ресурси;
- як отримуються промпти;
- як надсилаються сповіщення;
- як повертаються помилки.

Рівень даних MCP побудований на JSON-RPC.

Скажімо, виявлення інструментів — це `tools/list`.

Виклик інструмента — `tools/call`.

Читання ресурсу — `resources/read`.

Отримання промпта — `prompts/get`.

Зверніть увагу: MCP — це не довільно написані кілька HTTP-шляхів.

Він має власні методи протоколу, структури запитів і відповідей.

### 2. Транспортний рівень: визначає, як передаються повідомлення

Транспортний рівень доставляє ці повідомлення JSON-RPC.

Поширених варіанти два.

**stdio.**

Локальні процеси спілкуються через стандартні потоки вводу-виводу.

Скажімо, Claude Desktop запускає локальний MCP Server файлової системи й спілкується з ним через stdio.

Цей спосіб пасує локальним інструментам: швидко, без мережі.

**Streamable HTTP.**

Спілкування з віддаленим Server через HTTP, з підтримкою потокових можливостей і стандартної автентифікації.

Скажімо, підключення до віддаленого Sentry MCP Server або внутрішнього MCP-шлюзу компанії.

Цей спосіб пасує віддаленим сервісам, багатокористувацьким сценаріям і випадкам, де потрібні автентифікація й авторизація.

![Два рівні MCP: рівень даних визначає семантику, транспортний відповідає за передавання](https://file1.kamacoder.com/i/web/20260520112741_mcp_protocol_04_layers_transport_compressed.png)

Тож на співбесіді не обмежуйтеся фразою:

«MCP — це протокол для інструментів».

Скажіть:

> «Рівень даних MCP побудований на JSON-RPC і визначає семантику інструментів, ресурсів, промптів, життєвого циклу й сповіщень; транспортний рівень відповідає за передавання повідомлень, зазвичай це локальний stdio або віддалений Streamable HTTP».

Звучить помітно професійніше.

## 5. MCP Server надає три типи можливостей: Tools, Resources, Prompts

Це найважливіша частина MCP.

MCP Server може надавати не лише інструменти.

Він надає три типи можливостей: **Tools, Resources, Prompts.**

Їх обов'язково треба розрізняти.

### 1. Tools: дії, які модель може викликати самостійно

Tools найбільше схожі на Function Calling.

Це функції, які модель може викликати активно.

Наприклад:

- запит замовлення;
- пошук у логах;
- створення заявки;
- надсилання повідомлення;
- запит до бази даних;
- зміна файлу.

Tool зазвичай має назву, опис і схему параметрів.

Модель за питанням користувача й контекстом вирішує, чи викликати його.

Одним реченням:

**Tools відповідають на питання «які дії агент може виконувати».**

### 2. Resources: джерела даних, що дають контекст

Resources — це контекстні дані для читання AI-застосунком.

Вони радше «пасивно надають інформацію».

Наприклад:

- вміст файлів;
- схема бази даних;
- документація API;
- вподобання користувача;
- дані календаря;
- README проєкту.

Resources не обов'язково є дією, яку модель викликає активно.

Часто їх читає Host або застосунок за потреби й кладе в контекст.

Одним реченням:

**Resources відповідають на питання «що агент може бачити».**

### 3. Prompts: перевикористовувані шаблони промптів

Prompts — це заздалегідь описані шаблони взаємодії.

Наприклад:

- «сплануй мені подорож»;
- «підсумуй нараду»;
- «за логами помилок сформуй кроки діагностики»;
- «напиши опис PR за стандартами компанії».

Prompt може підказати моделі, як саме користуватися певними інструментами й ресурсами.

Одним реченням:

**Prompts відповідають на питання «за яким сценарієм агенту діяти».**

![Три типи можливостей MCP: Tools — дії, Resources — контекст, Prompts — сценарії](https://file1.kamacoder.com/i/web/20260520112742_mcp_protocol_05_primitives_compressed.png)

Є зручний спосіб запам'ятати:

**Tools — що можна робити.**

**Resources — що можна бачити.**

**Prompts — як робити надійніше.**

Багато хто зводить MCP до «протоколу виклику інструментів», і це надто вузько.

Насправді MCP прагне стандартизувати:

**спосіб з'єднання між AI-застосунком і зовнішнім контекстом.**

Інструменти — лише найпомітніша його частина.

## 6. Як приблизно проходить один виклик інструмента через MCP

Зберімо все на простому прикладі.

Користувач питає в AI-застосунку:

«Дізнайся, чому вчора ввечері гальмував платіжний сервіс».

Припустімо, Host уже підключив MCP Server моніторингу й MCP Server логів.

Процес приблизно такий.

**Крок 1: ініціалізація з'єднання.**

Host створює Client для кожного MCP Server.

Client і Server ініціалізують протокол, узгоджують версію й можливості.

Скажімо, Server повідомляє, що підтримує tools і resources.

**Крок 2: виявлення інструментів.**

Client надсилає Server запит `tools/list`.

Server повертає перелік своїх інструментів, наприклад:

- `query_api_latency`
- `search_service_logs`
- `get_deploy_records`

Host зводить їх у перелік інструментів, придатний для моделі.

**Крок 3: модель вирішує викликати інструмент.**

Побачивши питання користувача, модель вирішує спершу викликати `query_api_latency`.

Вона формує назву інструмента й параметри.

**Крок 4: Client викликає MCP Server.**

Host через відповідний Client надсилає `tools/call`.

MCP Server виконує реальний запит і повертає структурований результат.

**Крок 5: модель робить висновок за результатом.**

Якщо затримка почала зростати о 22:10, модель може викликати інструмент історії релізів.

Якщо виявиться, що о 22:05 був реліз, вона викличе інструмент логів.

І ми повертаємося до циклу ReAct, про який ішлося раніше.

MCP тут відповідає за підключення інструментів і протокол виклику.

А планування, судження й самоперевірка агента лишаються за моделлю й логікою застосунку всередині Host.

![Процес виклику інструмента через MCP: ініціалізація, виявлення, виклик, висновок за результатом](https://file1.kamacoder.com/i/web/20260520112743_mcp_protocol_06_call_flow_compressed.png)

Одна деталь.

MCP Server зазвичай не вирішує, «що саме відповісти користувачеві».

Він лише надає можливості.

Перетворює результати інструментів на відповідь саме AI-застосунок у Host.

Тож не сприймайте MCP Server як повноцінного агента.

Це радше стандартизований постачальник можливостей.

## 7. Чому MCP пасує агентам

Чого агент боїться найбільше?

Не відсутності інструментів.

А того, що їх забагато, вони розпорошені й неуніфіковані.

Цінність MCP для агента складається з чотирьох речей.

### 1. Стандартизоване підключення інструментів

Без MCP кожен AI-застосунок пише власний шар адаптації інструментів.

З MCP постачальник надає можливості за стандартом.

Хосту достатньо підтримувати MCP — і він підключить будь-який Server.

Це помітно знижує вартість інтеграції.

### 2. Динамічне виявлення інструментів

У класичному Function Calling перелік інструментів зазвичай зашитий розробником у коді.

У MCP Client може надіслати Server запит `tools/list` і динамічно дізнатися, які інструменти зараз доступні.

А якщо інструменти змінилися, Server може повідомити Client сповіщенням.

Для великої агентної платформи це дуже важливо.

Бо інструменти не є незмінними.

### 3. Контекст і дії розділені

Tools — це дії.

Resources — це контекст.

Prompts — це шаблони.

Це чіткіше, ніж загортати геть усе у функції.

Скажімо, схема бази даних доречніша як Resource.

А SQL-запит — як Tool.

Уміння пояснити це на співбесіді дуже додає балів.

### 4. Природніше комбінування інструментів

Один Host може підключити кілька MCP Server.

Наприклад:

- Server файлової системи;
- Server GitHub;
- Server бази даних;
- Server Sentry;
- Server корпоративної бази знань.

Host зводить ці можливості разом, і модель може комбінувати їх навколо однієї задачі.

Саме це агенту й потрібно.

![MCP робить агента придатнішим до комбінування інструментів: різні Server надають різні можливості, Host їх зводить](https://file1.kamacoder.com/i/web/20260520112744_mcp_protocol_07_agent_value_compressed.png)

Але зверніть увагу.

**Те, що MCP стандартизує підключення, не означає, що агент автоматично стає надійним.**

Поганий опис інструмента, поганий дизайн параметрів, погані межі прав — MCP цього не врятує.

Принципи дизайну інструментів із попередньої статті лишаються чинними.

MCP стандартизує лише «як підключати».

А не розв'язує автоматично «як спроєктувати хороший інструмент».

## 8. Як обирати між локальним і віддаленим MCP

MCP Server може працювати локально або віддалено.

Ці сценарії дуже різні.

### 1. Локальний MCP: файли, командний рядок, середовище розробки

Локальний MCP Server зазвичай використовує stdio.

Host запускає локальний процес і спілкується через стандартні потоки.

Пасує для:

- читання локальних файлів;
- пошуку по коду;
- роботи з локальним репозиторієм Git;
- запуску локальних скриптів;
- доступу до тимчасового середовища на машині розробника.

Переваги — швидкість, простота, відсутність мережевих витрат.

Недоліки — сильніша залежність від локального середовища й потреба уважніше ставитися до локальних прав.

Скажімо, Server файлової системи в жодному разі не має за замовчуванням відкривати весь диск.

Каталоги доступу треба обмежити.

### 2. Віддалений MCP: корпоративні сервіси й платформні можливості

Віддалений MCP Server зазвичай використовує Streamable HTTP.

Пасує для:

- корпоративної бази знань;
- платформи моніторингу;
- платформи логів;
- системи заявок;
- CRM;
- внутрішнього шлюзу до баз даних;
- SaaS-сервісів.

Переваги — централізоване розгортання, єдина автентифікація, зручність для багатьох користувачів.

Недоліки — доводиться опрацьовувати автентифікацію, авторизацію, мережеву затримку, аудит і ізоляцію орендарів.

![Локальний і віддалений MCP: один ближчий до середовища розробки, другий пасує платформним сервісам](https://file1.kamacoder.com/i/web/20260520112746_mcp_protocol_08_local_remote_compressed.png)

Тож вибір можна сформулювати так:

**локальні файли, код і інструменти розробки — локальний MCP.**

**Корпоративні системи, спільне використання й централізована автентифікація — віддалений MCP.**

Не варто робити все локальним.

І не варто робити все віддаленим.

Дивіться, де лежать дані, як керуються права й хто цим користується.

## 9. Межі безпеки MCP не можна покладати на свідомість моделі

MCP спрощує підключення інструментів до AI-застосунків.

Але що простіше підключення, то помітніші проблеми безпеки.

Про це обов'язково треба говорити.

Інакше на співбесіді, якщо ви лише хвалитимете MCP, інтерв'юер легко спитає:

«А як контролюються права інструментів? Чи не отримає MCP Server даних, яких не має отримувати? Що робити зі шкідливим інструментом?»

І ви застрягнете.

Межі безпеки MCP тримаються передусім на Host.

Host відповідає за те:

- до яких Server підключатися;
- які права давати кожному Server;
- чи потрібне підтвердження користувача перед викликом інструмента;
- який контекст передавати Server;
- чи дозволено виконувати високоризикові дії;
- чи піддаються виклики аудиту.

Server теж має бути стриманим.

Server не повинен за замовчуванням читати весь контекст.

Не повинен за замовчуванням мати доступ до всіх файлів.

Не повинен писати описи інструментів так, щоб вводити модель в оману.

Не повинен нишком розширювати свої права.

Особливо це стосується високоризикових дій:

- видалення файлів;
- зміна коду;
- надсилання повідомлень;
- зміна бази даних;
- оформлення замовлень;
- виконання команд;
- виклик продакшн-інтерфейсів.

Модель не може викликати це «коли їй заманеться».

Мають бути обмеження прав, підтвердження користувача й записи для аудиту.

![Межі безпеки MCP: Host керує правами, Server надає обмежені можливості, високоризикові дії потребують підтвердження](https://file1.kamacoder.com/i/web/20260520112747_mcp_protocol_09_security_boundary_compressed.png)

Тож запам'ятайте:

**MCP — це не магія безпеки.**

Він дає стандартний протокол і простір для проєктування меж.

Але безпека зрештою залежить від того, як Host керує правами, як Server надає можливості і як інструменти роблять підтвердження й аудит.

Це змикається з попередньою статтею про дизайн інструментів.

Щойно йдеться про зовнішні дії, треба діяти за правилами інженерної безпеки.

## 10. Як описувати проєкт із MCP у резюме

Якщо ви робили щось із MCP, не пишіть у резюме просто:

«Підключив MCP Server, реалізував виклик інструментів агентом».

Це надто поверхово.

Опишіть, яку інженерну проблему ви розв'язали.

Наприклад:

> «На основі MCP підключив внутрішню базу знань, систему заявок і платформу логів; виніс логіку адаптації інструментів, раніше зашиту в агента, в окремі MCP Server; реалізував виявлення інструментів, валідацію схеми параметрів, аудит викликів і контроль прав; забезпечив динамічний виклик агентом інструментів моніторингу, логів і історії релізів у сценарії діагностики збоїв».

Це вже схоже на проєкт.

Тут видно кілька речей:

- ви розумієте, що MCP — протокол підключення інструментів;
- ви розумієте, що Server має окремо інкапсулювати можливості;
- ви зробили виявлення інструментів і валідацію параметрів;
- ви подумали про аудит і права;
- ви вмієте помістити MCP у конкретний бізнес-сценарій.

Або так:

> «Спроєктував MCP Server для підтримки клієнтів із інструментами запиту замовлення, запиту доставки, перевірки правил повернення й створення чернетки повернення; статус замовлення та документи з правилами повернення надав агенту як Resources, щоб не запихати всі бізнес-дані в промпт, що підвищило стабільність викликів і зручність супроводу».

Це значно сильніше за «зробив розумного агента підтримки».

## 11. Як інтерв'юери питають про MCP

Наостанок — кілька частих формулювань.

**Питання: що таке MCP?**

Можна так:

> «MCP, тобто Model Context Protocol, — це протокол, за яким AI-застосунки стандартизовано підключаються до зовнішніх інструментів, джерел даних і шаблонів промптів. Він використовує архітектуру Host-Client-Server: Server надає Tools, Resources і Prompts, Host через Client підключає кілька Server і передає ці можливості моделі».

**Питання: чим MCP відрізняється від Function Calling?**

Можна так:

> «Function Calling ближчий до моделі: він розв'язує, як модель обирає функцію й формує параметри. MCP ближчий до рівня підключення в застосунку: він розв'язує, як інструменти, ресурси й промпти виявляються, підключаються й викликаються AI-застосунком. У реальній системі Host може отримати перелік інструментів через MCP, а потім перетворити його на формат Function Calling для моделі».

**Питання: які основні ролі в MCP?**

Можна так:

> «Основні — Host, Client, Server. Host — це AI-застосунок, що відповідає за взаємодію з користувачем, виклик моделі, права й зведення контексту. Client — компонент усередині Host, що з'єднується з конкретним Server. Server надає інструменти, ресурси й шаблони промптів. Один Host може мати кілька Client, і кожен зазвичай відповідає одному Server».

**Питання: як розрізняти Tools, Resources і Prompts?**

Можна так:

> «Tools — це дії, які модель може викликати активно: запит до бази, надсилання повідомлення. Resources — контекст лише для читання: вміст файлів, схема бази даних, документація API. Prompts — перевикористовувані шаблони, що підказують моделі, за яким сценарієм користуватися інструментами й ресурсами. Простіше кажучи, Tools — що можна робити, Resources — що можна бачити, Prompts — як це робити».

**Питання: які ризики безпеки має MCP?**

Можна так:

> «MCP стандартизує підключення інструментів, але це не робить систему безпечною сама собою. Host мусить контролювати права підключення до Server, обсяг переданого контексту й підтвердження для високоризикових інструментів; Server має надавати мінімально необхідні можливості й не мати за замовчуванням доступу до всіх даних. Інструменти з побічними ефектами — видалення файлів, надсилання повідомлень, зміна бази даних — потребують підтвердження користувача, перевірки прав і записів для аудиту».

Такої відповіді загалом достатньо.

## 12. Не робіть із MCP культу

MCP важливий.

Але не варто його обожнювати.

Це не всемогутній фреймворк агентів.

Використання MCP не змусить агента автоматично планувати, самоперевірятися й ставати надійним.

MCP розв'язує проблему з'єднання.

Він дозволяє інструментам, ресурсам і шаблонам промптів стандартно підключатися до AI-застосунків.

А чи зможе агент стабільно виконувати задачі, залежить ще й від того:

- чи чіткий опис інструментів;
- чи строга схема параметрів;
- чи дозволяє формат відповіді вирішити наступний крок;
- чи задані межі прав;
- чи можна відновитися після помилки;
- чи керує Host вибором інструментів і контекстом;
- чи є підтвердження й аудит для високоризикових дій.

Тож розуміти можна так:

**Function Calling — це спосіб, яким модель викликає інструмент.**

**MCP — це стандартний протокол підключення інструментів до AI-застосунку.**

**Агент — це система, що безперервно діє задля мети.**

Вони не замінюють одне одного.

Вони розв'язують різні проблеми на різних рівнях.

Якщо ви чітко поясните цей зв'язок, інтерв'юер зрозуміє, що ви не женетеся за модними словами.

Ви справді знаєте, де саме MCP стоїть в інженерії агентів.
